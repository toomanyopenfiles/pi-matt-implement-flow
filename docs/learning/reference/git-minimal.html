git 最小词典（为本插件的工作流定制）

只收录编排流程里真正出现的命令与概念 · 不追求完整，追求够用

A五个概念，一个心智模型

把 git 想成一间档案室：

  • commit（提交）＝一份不可修改的快照，加一个 40 位十六进制的指纹编号（SHA）。通常只报前 7 位就够定位。commit 一旦产生就永远在那，不会因为分支移动而消失。
  • branch（分支）＝一张写着某个 SHA 的标签纸。分支不是容器，就是一个可以挪动的名字。git branch -f 的本质是：把标签纸撕下来贴到新的 SHA 上。
  • HEAD＝「你现在站在哪」的指针。
  • merge-base＝两个分支的共同祖先 commit。三点 diff 从它出发（见 0001 答疑）。
  • 干净 / 脏＝git status --porcelain 有没有输出行。空输出＝干净。⚠️ 未跟踪的文件（??）也算脏。

B本工作流用到的全部命令

命令人话解释谁 · 何时
git status --porcelain机器可读的「改动清单」，一行一个文件；空输出＝工作区干净。派发前的门卫编排者 · 每轮派发前
git rev-parse <分支名>把分支名翻译成 40 位真 SHA——「问 git 要真相」的标准动作，不信任何人的报告编排者 · 锚定与修复轮
git branch ticket-01 <SHA>在指定 SHA 上创建分支（已有同名会报错）编排者 · 锚定
git branch -f ticket-01 <新SHA>强制移动已有分支到新 SHA（标签纸重贴）。修复轮的「票分支前移」编排者 · 修复完成后
git branch -D ticket-01强制删除分支（小写 -d 要求已合并才肯删，大写不问）编排者 · 票合并关闭后清理
git merge --no-ff ticket-01把票分支合并进当前分支，强制产生一个合并提交（原因见 0001 答疑）编排者 · 每票串行合并
git diff base...ticket-01从共同祖先开始比较，只显示票 01 独有的改动（三个点，不是两个）编排者 · 写 review bundle
git log --oneline每行一条提交历史：SHA 前 7 位 + 提交说明。bundle 里的第二件东西编排者 · 写 review bundle
git worktree list列出主检出和所有 worktree 的路径与所在分支。对账用（压缩后恢复现场第一步）编排者 · 恢复/清理前
git worktree remove --force <路径>删除一个 worktree 目录（force 跳过安全检查——所以删除前必须先自检干净）编排者 · 清理阶段
cd <路径> && npm test进入 coder 的 worktree 目录跑全量测试——修复轮的「代跑门」编排者 · 修复轮

D两个高频误读

  • 「git status 显示干净」≠「所有提交都已合并」——干净只说明没有未保存的改动；提交可能在任何分支上。所以本流程用 rev-parse 查分支位置，而不是用 status 判断进度。
  • 「分支删了 = 提交丢了」——不一定。commit 是档案室里的实体文件，删标签纸不影响快照本身；只要还有别的标签（或 SHA 还在日志里）就找得回。但「没有标签又没记 SHA」的 commit 最终会被垃圾回收——这就是台账里优先记 SHA的原因。
