# ADR-0009: Prompt-driven 修复与未封账 run 续跑——可靠事实不等于机械编排判断

- **Status:** accepted（spec #12 已确认；本 ADR 先于组件实现落盘，不表示代码已完成切换）
- **Date:** 2026-10-07
- **Deciders:** 本包维护者（spec #12 需求与测试边界确认；正常封账门在实现前置设计中确认）
- **Context tags:** repair, formal-review, run-continuation, reconciliation, partial-delivery, abandonment

取消累计修复次数配额，把继续、人工暂停、恢复与交付判断留给编排器依证据作出；脚本仍
独占记账与台账写权、报告差异并守住明确事实校验。代价是复杂处置更依赖模型读取证据
和遵守 prompt，而不是获得新的机械正确性保证。

## Context

缺陷 #11 暴露：预算耗尽后，问题即使被撤回，也无法在同一 run 取得新的正式批准；
修复数绑定评审轮次迫使人为制造修复才能重审，升级历史还会永久覆盖最终合并状态。
集成另有循环阻塞：实际合并后须通过集成验证才记 merge，未入账合并使 check 非零，
“差异一律停止”却禁止派出直接修复集成的 coder。固定两次失败停止并未解决这些问题。

原封账门把 not_ready 警告放行当作隐式放弃，仍要求有 merge 就先补 final；全升级也能
充作票闭环。这无法表达中途明确放弃与正常完整交付的区别。用户接受 A、B 已完成而
C 尚缺权限时，若走完整收尾又会关闭 spec、删快照并封账，使同 run 续跑丧失依据。

spec #12 选择取消配额而非 #11 原提议的预算恢复方案；单问题撤回不等于完整批准的
安全要求仍保留。ADR-0001/0007 的事实写权、tracker 数据契约与 ADR-0008 的机械门禁
不是问题来源，不扩大脚本为 workflow 引擎。

## Decision

### 1. 判断归编排器，事实校验归脚本

逐票、集成、终审修复共享同一原则：有合理、在批准范围内的下一步就继续；缺需求
决定、权限、外部条件，或无法提出有依据的下一步则人工暂停。连续失败促使重审办法，
不是自动终止。每次返回核对实际行动、验证结果、新问题/范围变化与合理下一步；这是
思考框架，不新增报告 schema。新诊断证据可以是进展，提交数量、措辞变化或更换 agent
不能充当进展证据；不得削弱测试、验收标准或安全约束制造表面成功。

移除有效修复预算、预算 UI 及执法，也移除集成/终审连红两次必须停的规则。未封账旧
run 立即采用新规则，恢复时说明变化；旧设置、init 字段与事件保持可读、不自动改写。
命令超时、并发上限、取消能力仍保留，但无次数配额不承诺总时间或费用有限。

脚本继续负责合法载荷、初始化与不可逆封账、序号/信封、append-only 写入、台账再生、
明确事实校验与差异报告。不增加停滞检测、进展评分、失败指纹、固定无进展窗口、专用
停滞 agent、frontier 引擎或大型工作流引擎，也不解析笔记裁定授权/处置/审批有效性。

### 2. 修复与正式评审独立

修复编号仍描述尝试顺序，不是配额；正式评审轮次独立描述评审顺序，不等于 fix 数加一。
保留正整数等载荷校验、修复顺序编号和同票同轮 verdict 去重。允许一次评审后多次修复，
也允许无新增代码修复的后续完整评审。普通澄清、单问题撤回或 notes 不替代 approved；
最近正式裁决仍为 changes_requested 时不能因此合并（reviewer=off 的既有例外保留）。
编排器保证必要审批与验证证据对应当前候选代码，不新增证据有效性检测引擎。

代码修复仍由完整命名的 coder 执行，不由主 agent 修 feature。逐票隔离 worktree、
retained resume 与手跑机械报告门禁保留；集成/终审 fixer 在主 feature worktree 串行
工作，使用既有纯判定 gate。通用 coder 说明不能迫使非隔离 fixer 另开树。

终审修复后逐项核对 findings 与证据。局部明确问题可由编排器核对后继续；涉及需求、
行为、较广影响或证据不足则重审，核对结果与选择写编排笔记。历史 final 始终保留，
旧裁决或测试绿不自动证明新代码合格，不增终审修复验收事件。

### 3. 历史事实与当前处置分开

票级 escalate 保存人工交接历史，待决策问题、用户决定、run 暂停阶段及恢复说明归
编排笔记。不新增暂停、恢复、授权或预算追加事件，不把普通需求决定记为 anomaly。
升级既不是票完成，也不满足依赖或正常封账条件；后续 merge 显示完成且保留升级历史。
已升级未合并时，编排器结合后续事实和笔记解释当前行动，不要求脚本还原每个暂停瞬间。

anomaly 及合法旧事件引用保留，处置结果与证据指针归笔记。历史异常本身不禁止收尾，
也不能被描述为必然尚未解决；无法机械核验时提示阅读证据。笔记承载决策，但不撤销
事实、归零编号、代替正式批准或绕过有效校验；保留已有确有依据的补正/恢复标注。
缺少可靠证据时核查或交给用户，不擅自断言已恢复，不新增异常解决或通用事件更正体系。

### 4. 对账差异可恢复，但不能掩盖

check 保持非零退出和完整差异。非零后暂停普通派发、后续票合并和收尾；编排器核实并
说明差异后，可执行直接解决该差异的恢复动作。解释不了的差异先核查或交给用户。
例外不绕过 schema、提交存在性、有效审批与封账不可逆性。

保持实际合并 → 集成验证通过 → merge 记账 → 票完成的既有顺序。未入账合并仍令
check 非零，但可以为它派发集成 fixer；不得提前记成功 merge 或关闭票来变绿。
用已有事实、工作流产物与笔记重建阶段，不新增待集成验证事件或修复子状态机。

### 5. 阶段性交付不终结 run

须用户明确接受，先核验已完成部分可交付性，记录交付内容、未完成项及影响、风险与
用户决定，报告分支/提交/验证证据。run 保持未封账，tracker 快照与续跑证据保留；
不执行完整 seal 同步、spec 关闭、最终快照清理或 ready-to-close 收尾链，不新增部分
tracker 同步模式，不包含自动发布或拆出独立 PR/MR。running 表示未终结，不意味着
此刻有 child 执行；阶段性交付不是放弃剩余范围。

续跑同一未封账 run 要重读流程、build、check、读取笔记与证据、核验新条件；不重复
init、不重拉延迟 tracker 状态、不重复实现/合并已完成 A、B，只继续未完成 C。已封账
run 仅留历史，永不重开。

### 6. 正常完成与用户放弃采用不同封账结果

沿用 `close` 事件，新增 `--outcome completed|abandoned`（载荷键 `outcome`）。省略旗标
时，新写入按正常完成语义并记录 `completed`，不是根据旧历史猜意图。已有 tracker
同步模式 `abandon` 是动作名，close 结果 `abandoned` 是终结状态；两者不互换，也不新增
事件类型、同步模式或绕过校验的旗标。

- **completed**：完整交付后依契约幂等同步、就绪收尾、最终清理与封账。普通 close 不
  以 escalate 替代票完成，保留既有 spec 母票、wontfix、resolved 研究票等非任务票豁免。
  有合并工作的 run 必须已有 final，最新裁决须 ready 或 ready_with_fixes；凡 latest
  final=not_ready 均拒绝正常封账，不再以警告放行充当隐式放弃。零合并仍沿用不要求
  终审的既有边界，但全升级不因此成为完整交付。编排器仍核验当前代码与证据，不能把
  机械门满足或历史 ready_with_fixes 当作自动交付证明。
- **abandoned**：仅在用户明确放弃时使用。先停止相关 child、保存代码与证据、说明
  未完成项，再按 tracker 契约处理放弃说明与占坑；失败则开放、记异常并处理，成功
  后显式放弃封账。不要求补 final 或逐票升级，也不要求未完成票闭环；仍校验合法
  输入、已初始化与未封账。不得关闭未完成票、标代码 ready 或声称完整交付。
- **旧 close**：无 outcome 的已封账记录继续 build/check/审计可读，不重写，不按新的
  写入门追溯否定其合法性；缺少明确结果时展示为旧记录/结果未记录，不推断 completed
  或 abandoned 历史意图。旧明确放弃证据亦保持原样，不反填事件字段。任何已封账
  run 都拒绝全部新事件，包括再次 close 或 anomaly。

## Alternatives considered

- **保留预算并追加授权/重置**：将用户介入继续用于配额管理，未解决评审与修复耦合；
  与本次用户选择相反。预算耗尽不再推断为当前阻塞，历史预算仍供审计。
- **机械停滞判定或完整恢复状态机**：可增加确定性约束，却要硬编码“什么是进展”并
  增加事件、迁移和复杂裁定面；复杂问题判断仍不可靠，本 spec 明确不建设。
- **差异一律停 / 提前记 merge**：前者阻断必要集成恢复，后者伪造验证成功。选择保留
  非零差异且限于直接恢复，接受编排器解释差异的责任。
- **延续隐式弃跑 / 所有退出都要求终审**：分别混淆交付意图与迫使用户补造无用步骤；
  选择 close 明确结果，接受写入默认与旧字段缺失读法必须分开的兼容成本。
- **部分交付走完整收尾或新增部分同步**：前者毁掉续跑条件，后者扩大 tracker 生命周期；
  本次选择保留开放 run 与本地成果，接受远端进度继续延迟。

## Consequences 与验证边界

这是难逆转的职责边界调整：配置、事件写点、prompt、自检与审计必须一起改变，旧预算
不能通过某个未更新的提示词或审计风险推断回流。未来读者可能误把笔记视为状态漏洞或
要求更多事件；本决策有意保持机械事实可靠而不将所有编排判断机械化。

确定性测试沿用 CLI 黑盒真实临时 git 仓、合成票、PATH tracker 命令桩与既有配置/审计/
prompt 自检入口：验证次数不再拒绝、独立评审及重复拒绝、最新正式批准门、升级后合并
投影与历史、未入账合并 check 仍非零、显式封账与旧记录字节不变、同步失败重试与票
保持开放，以及阶段性交付轨迹中的开放状态/快照留存。静态自检只证明约定在文本中。

继续/暂停、直接差异恢复、终审重审选择、用户接受阶段性交付、实际停止 child 等须
另保留可复查场景动作与证据；合成 CLI 顺序不能冒充模型自主选择。测试不保证模型每次
判断正确，不保证无次数配额的总资源消耗有限，不新增生产测试钩子或强制 LLM CI。
