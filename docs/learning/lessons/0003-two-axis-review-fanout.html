两轴 review 与嵌套 fanout：reviewer 怎么审一张票

使命：维护并演进这个插件 · 预计 15 分钟 · 前置：0002 一张票的旅程

开课前 1 分钟 本课聚焦 0002 总表的第 ④ 步，把它拆到可维护的粒度：reviewer 收到什么、自己干两件什么事、派出去的两个「轴 child」各自查什么、判决怎么聚合出来。本课没有新 git 命令——reviewer 全程没有 bash，这正是它「只读」属性的一部分。角色配色沿用：赭石=编排者、蓝=coder 家族、绿=reviewer 家族。

§1reviewer 的一票审查（六步总表）

步执行者干什么（目标）输入 → 输出
①reviewer 先核对实况：读 bundle、票、spec、自己 worktree 里的变更文件，把 coder 报告的每一条 claim 和现实对一遍——不信任报告 bundle 路径 + 票 + spec + 门证据 + coder 报告 → 读到位的事实底座
②reviewer 找标准源：仓库里的 CODING_STANDARDS.md / CONTRIBUTING.md 等（找不到就明说） worktree → Standards 轴要引用的标准源清单
③reviewer 一次顶层 workflow 调用（async: true）派出两个轴 child，都是 context: "fork"——继承自己的阅读成果 两条自足的轴 brief（每条都带全部路径与指令）→ 两个并行轴 child
④Standards 轴（fork child） 查文档化标准的违反（每条引用被违反的标准条目：文件+规则）+ 逐条过味道基线（具名并引用）；区分硬违规与判断题 轴 brief → 轴报告（≤400 词）
⑤Spec 轴（fork child） 查：spec 要求但缺失/只做一半的；diff 里没被要求却做了的（scope creep）；看着实现了但做错的。每条发现引用 spec 原句 轴 brief → 轴报告（≤400 词）
⑥reviewer 聚合：两轴报告以 ## Standards / ## Spec 并列呈现，不合并不重排；给每轴条数 + 每轴最重问题；出结构化判决 两轴报告 → verdict（approved/changes_requested）+ findings（severity/file/line/issue）
严重度纪律（两个 reviewer 都遵守） P0 挡合并；P1 发布前该修；P2 仅记录。按证据过滤，不按严重度过滤：只报能从 diff、worktree 或契约矛盾里证实、且由本票改动引起（或使其可达）的问题。某轴零发现时，精确写 No issues found.——一个字都不多。

§3为什么两轴要分开、聚合为什么「不重排」

  1. 两轴的坐标系不同：Standards 轴问「这符不符合仓库的规矩」；Spec 轴问「这做的是不是被要求的事」。混在一份清单里，一个「变量名不合 glossary」和一个「验收标准没实现」会变成同一列里的两个格子——权重失真。
  2. 不合并不重排：排序本身就是判断。reviewer 的职责是呈现证据，把「怎么权衡」留给编排者（编排者手里还有 git 真值和集成门）。裁决词只有两个：approved / changes_requested——绝不出现 blocked（lane 语义保留字）。
  3. 轴 child 仍然自足：fork 继承的是评审者的阅读上下文，但每条轴 brief 依旧带全部路径与指令——这是 multi-lane 纪律「every child packet must stand alone」。fork 是便利，不是依赖。
  4. 轴 child 是终点：它们只读、不能再派孙代。嵌套深度默认两层（main → reviewer → 轴 child），由平台的递归守卫强制；reviewer 的 frontmatter 里 subagent 工具和 allowNestedSubagents: true 是显式授权，不是默认。

§4final-reviewer：同一套两轴，多一双「跨票眼」

reviewer（每票）final-reviewer（整条分支）
审查范围一张票的三点 difffeature-base...HEAD 全分支 diff
两轴流程相同（①–⑥）相同
特有职责—跨票狩猎：跨文件漂移、组件互相矛盾、spec 有要求但没有票实现它、文档与交付代码脱节
额外工作—裁定先前每票 review 里被延后的 minor 发现：现在修还是继续延，逐条给理由
判决词表approved / changes_requestedready / ready_with_fixes / not_ready

为什么「跨票狩猎」只有 final-reviewer 能干：每票 reviewer 的 worktree 里只有自己那张票的树；整条分支拼完之后，「组件 A 的接口假设和组件 B 的实现漂了」这类问题才第一次变得可见。这就是 0001 里「最终门」存在的全部理由。
