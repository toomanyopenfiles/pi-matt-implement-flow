pi-matt-implement-flow · 课程 0001

一张图记住整个工作流：流水线与轮次循环

使命：维护并演进这个插件 · 预计 10–15 分钟 · 建议先复述再点练习

你是这个插件的维护者。要改它，先要能从记忆里完整画出来它的运行骨架。 这节课只教一件事：编排循环的高层形态——哪里是单行道，哪里是循环体，循环什么时候退出。 细节机制（worktree 保留、resume、验收契约）留给后续课程，本课只建立骨架。

§1全景：一条流水线，嵌着一个循环

三条通道读法：

  • 单次执行：前置检查 + Round 0（读 spec 与全部票入台账 → 建 feat/<slug> 分支 → 跑一次全量测试记基线 → 有远端就开 draft PR）。
  • 循环体：每轮从①到⑥走一遍，⑥ 之后重算前沿，还有票就回到①继续派发。这就是为什么它不需要人工逐票推进（D13：async 完成唤醒同一 session 起新 turn）。
  • 出口：所有票关闭或升级后，才进最终门——对整条分支做两轴 review，这是唯一能看到跨票问题的关口。

维护者最易踩的一处 SKILL.md 原文反复强调：派发必须用全名。裸名 coder 会解析到用户级 worker 别名（你的环境里它存在！），裸名 reviewer 会解析到内置 agent——两者都不是这个包的 persona。这不是风格问题，是注册命名空间隔离（D10）。

§3状态存在哪里？只有三处，没有对话记忆

  1. git 真值（分支名、SHA、diff）——一切判定的最终依据。run status 和子代理的散文报告只是线索：§10.11 实测出现过 run 判 failed 但 commit 已落地，甚至 coder 伪造全长 SHA（§10.18-4）。锚定一律先 git rev-parse 取真值。
  2. 台账 .pi/matt-implement/<slug>/ledger.md（被 .gitignore 覆盖，天然不脏树）：每轮开头读、每次状态变化后重写。它的存在理由是跨上下文压缩的记忆——压缩后重读 skill + 台账 + git worktree list 先对账，再派发。
  3. 票追踪器（本仓库采用 local markdown：.scratch/<slug>/issues/）：认领 / 关票的权威。因为也被忽略，状态写入不会弄脏派发检查。
