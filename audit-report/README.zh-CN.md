# audit-report — 跑后审计报告

[English](./README.md) | 简体中文

一个纯本地的审计工具，针对一次未封账或已完成的 pi-matt-implement-flow 运行（run）：把这次 run 生成为
可浏览的静态报告网站，方便你检查整个流程的执行情况、暴露潜在问题。

**什么时候用**：暂停或阶段性交付时查看已保存的工作；合并前复核一次 run 的质量；事后定位
哪里出了问题；或者给这次 run 留一份可审计的记录。

- **不调用大模型**：全部内容自动收集自 run 的本地记录和 git 历史。
- **双语输出**：`--lang zh|en` 选择报告网站和全部输出的语言——页面文案、风险描述、警告、
  时间线叙述、名词表、分析简报、命令行输出（默认 `zh`）。事实与证据本身与语言无关。
- **不碰你的仓库**：工具只做读取，绝不修改你的运行数据和源码。报告默认写到运行目录下的
  `report/`（该目录已被 gitignore，`git status` 不会变脏）；用 `--out` 可以输出到别处，
  完全不触碰目标仓库。
- **事实与观点分开**：报告主体是事实——每条都可回溯出处。AI 分析是可选的（见下文），单独
  渲染成一个明确标注"非事实"的区块。
- **多出来的文件可以忽略**：报告目录里还会多一个 `model.json`，用了 `--ai-brief` 时再多一个
  `analysis-brief.md`，都是本工具的副产品，不是你仓库的文件。

## 用法

```bash
# 最简：对一次 run 生成报告（输出到 <运行目录>/report/）
node audit-report/report.js --runtime-dir <repo>/.pi/matt-implement/<slug>

# 输出到别处（如仓库外，完全不触碰目标仓库）
node audit-report/report.js --runtime-dir <...> --out /path/to/report-out

# 生成英文报告（默认中文）
node audit-report/report.js --runtime-dir <...> --lang en

# 导出 AI 分析简报（可选，见下文）
node audit-report/report.js --runtime-dir <...> --ai-brief

# 指定已填好的 AI 分析意见并重新渲染
# （可选；文件放在报告目录下则无需此参数）
node audit-report/report.js --runtime-dir <...> --ai-analysis <意见文件>.json
```

跑完后用浏览器打开 `report/index.html` 即可查看。

## 报告内容

| 页面 | 内容 |
|---|---|
| `index.html` | 运行总览（分支 / spec / 流程形态 / 测试门禁 / PR / 收尾结果）、运行统计、**异常与风险区**（按规则检出）、票目总表、叙述化事件时间线、用量与成本、名词表 |
| `ticket-NN.html` | 每张票的完整过程：票面原文 → 给实现者的任务要求 → 实现者的报告与验收详情（含测试门禁输出）→ 评审结论与问题清单全文 → 评审 diff → 修复轮 → 合并 |
| `final.html` | 整分支终审：结论与全文、异常与升级记录、收尾结果（正常完成、明确放弃，或未注明结果的旧记录）、编排笔记全文 |

任何一类证据缺失时，相关页面会明确标注，其余内容不受影响。
旧修复次数上限仍可作为历史记录查看，但不是当前尝试配额，也不是 run 无法继续的理由。
实际修复与完整评审证据仍保留；澄清或撤回一条问题不等于完整批准。

收尾结果说明 run 如何结束，不代表每份保存的改动都已可用。明确放弃会保留工作与证据，
但不等于完整交付或批准，未完成票仍保持开放。暂停会保留开放的 run，已封账的 run 不能
重开。旧收尾记录没有注明结果时，报告不会猜测是完成还是放弃。新的正常完成不能在终审
“未就绪”时收尾；已放弃的 run 和历史记录仍可能有这个裁决，报告会保留展示。

接受阶段性交付不是放弃，也不是完整交付。请查看笔记中的接受决定、已完成内容、分支与
提交引用、验证证据、未完成项及其影响、风险和续跑条件。未封账 run 会保留本地工单副本
和评审问题；spec 保持开放，PR / MR 不会标为可审查。`running` 表示尚未终结，不表示
当前有 agent 执行。请保留运行目录，待缺少的条件核验后继续同一个 run；只有全部工作
完成后，才正常收尾。报告不会证明已完成部分一定可用，也不会为你发布部分版本或拆出
独立 PR / MR。

设计见 [ADR-0009](../docs/adr/0009-prompt-driven-repair-and-run-continuation.md)。

曾交接给你、后来合并的票会显示完成，原升级、原因和后续工作仍可查看。未合并的交接票
不代表完成，也不能证明下游依赖已满足。历史中的升级或异常，本身不能证明当前仍有阻塞
或未解决的故障。请查看编排笔记和支持证据，了解决定、处置与续跑说明。无法核验时，报告
会提示你核对，不会仅凭笔记宣称已恢复或已批准。失败历史以及有证据支持的恢复、补正标注
仍会保留。

## 异常与风险区（按规则检出，不是模型推断）

全部条目由规则机械检出、可回溯出处。会被标记的情况：

- 有失败的子任务运行
- 验收被拒收
- 历史中有异常记录
- 历史中有升级记录
- run 没有正常收尾
- 带着问题收尾：收尾时最新终审结论是 `not_ready`
- 某次运行的证据缺失
- 某张票的任务原文没能恢复
- 同一张票 ≥2 轮评审要求修改

条目按严重度排序（高危 / 注意 / 背景）。另有三种标注会调整条目的呈现，但**风险条目一律不删除**：

- **"已恢复"降级**：某次失败或拒收，如果同一张票后来有更晚的成功把它补上了，降为"注意"并
  标注"后续运行已恢复"、附上恢复它的那次运行的链接；一直没有恢复的保持"高危"。降级最多到
  "注意"——工作确实被打断过——而且连续多次事故不会被一次后来的成功一笔勾销。
- **"已补正"标注**：当一条异常记录取代（更正）了更早的记录时，该异常降为"注意"并标注
  "已补正"，相关的证据缺失风险也带上这个标注。补正依据一并给出，供你复核。
- **无效的运行引用会被忽略**：明显不是真实运行 ID 的引用属于记账噪音——直接跳过，不会变成
  "证据缺失"风险，只在警告区留一条供你核对。

## AI 分析意见层（可选）

规则检测只能查"已知类型的问题"；藏在各处证据之间的语义矛盾值得让大模型看一遍。工具本身
绝不调用模型——用一个两步流程把事实与观点分开：

1. `--ai-brief` 导出 `analysis-brief.md`——一份自包含的证据简报，尾部附上分析结果的格式说明；
2. 把简报交给大模型（或在 pi 会话里分析），按说明写好 `ai-analysis.json` 后重跑本工具——
   报告目录下的文件会被自动读取；文件在别处时用 `--ai-analysis <文件>` 指定。

分析意见会渲染进独立的"AI 分析意见"区块，明确标注为非事实——用于提示可能的交叉矛盾与未建模
风险，采信前请对照证据核实。

## 排错

- **有些条目标注证据缺失？**——某一层证据没找到（比如 pi 会话记录已被清理），相关页面会注明
  缺了什么，其余内容不受影响。
- **继续工作后，异常或升级仍被列出？**——重试成功或后来合并后，历史仍会保留。请核对
  当前票状态、编排笔记和证据；仅有历史条目不代表问题当前仍存在。证据缺失表示结果还需
  核对，不能认定已经恢复。
- **报告说 run 已放弃？**——保存的工作并未被标为就绪。使用前请核对未完成项说明、
  评审问题与证据。
- **报告显示 `running`，但没有 agent 工作？**——run 仍未封账，可能已暂停或阶段性交付。
  请查看笔记中的阻塞、你的决定与下一步，保留运行数据供续跑。这不能证明有 agent 进程在执行。
- **语言不对？**——加 `--lang zh|en` 重新生成。
- **报告在哪？**——默认在运行目录的 `report/` 下；用了 `--out` 则在 `--out` 指定的位置。
